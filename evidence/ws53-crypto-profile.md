# WS53 安全子系统：应用配置与 IRQ/通道来源核对

以 SDK `163d9150ab94a02d09a05f623351f9facee3025e` 的
`ws53_liteos_app` 为基准，运行 `scripts/check_ws53_crypto_profile.py`，
逐份比对输入文件与该提交，再编译原始 IRQ 翻译单元及未修改的 HASH 分配函数。
OS、完成状态和硬件锁结果是主机桩；没有访问任何设备或密钥。

## 已核对事实

| 项目 | 原 SDK 编译/运行结果 | 适配约束 |
|---|---|---|
| SPACC/HASH/SYMC | 共同基址 `0x52010000`，应用配置启用 | 应建一个共享外设实例，不能把 HASH/SYMC 当独立独占控制器 |
| PKE | `0x52020000` | 使用自己的寄存器描述；ROM 微码、锁及初始化仍待审计 |
| KM | `0x52022000` | 密钥槽/派生共享资源，未授予安全独占 token |
| TRNG | `0x52024000` | 与已有 TRNG 来源一致，跨核消费者仍须协调 |
| FAPC | `0x53000000` | Flash 安全/在线解密关联，本轮不配置 |
| SPACC IRQ | 59，与应用核 `SEC_INT1_IRQN` 一致；本配置启用 | HASH/SYMC共享处理，不借用MDMA IRQ58 |
| RKP/KLAD IRQ声明 | 60/61，与 `SEC_INT2/3_IRQN` 一致 | 仅宏映射事实，未实测投递 |
| PKE IRQ声明 | 58，与应用核 `M_DMA_IRQN` 重号；应用配置关闭PKE IRQ | 路由未解决，不按该宏生成可用中断或启用它；不能推断真实PKE应为70 |

HASH和SYMC各配置两个软件硬件上下文，通道掩码均为`0xfffe`。原 HASH 分配函数
在16种“上下文已占用/硬件锁失败”组合中能返回通道1或2。原 IRQ 初始化却仅为
通道1注册等待函数，9种完成状态组合的分发也仅检查通道1。通道2完成不会触发该
分发器中的通知。SYMC分配函数源码同样使用`index+1`（尚未动态执行其完整分配函数），
而本次动态执行证明SYMC IRQ注册/分发也只有通道1。不要把这两种证据等级混为一谈。

两个算法共享中断；HASH1完成时原处理函数提前返回，不在同次调用检查SYMC。
这说明软件顺序，不证明硬件会丢中断；真实源保持/应答语义仍需后续寄存器核对。

应用先启动控制核和IPC，再调用安全环境初始化。初始化源码报告ACPU身份并使用
动态分配的内存；原HASH锁代码还读取并回查硬件所有者。以上均不证明Rust可以直接
取得排他所有权，必须审计跨核、时钟及DMA/缓存协议。

## 范围与重跑

结果及全部输入摘要见`ws53-crypto-profile.json`。两次独立临时目录执行结果逐字节相同。
没有新增RDL、PAC、HAL或QEMU模块，没有验证任何加密算法输出、硅片通道数、IRQ
线路、复位值或寄存器副作用；这些发现是实现前置证据，不能计作加密支持或实板通过。

```sh
uv run --script scripts/check_ws53_crypto_profile.py \
  --sdk /path/to/fbb_ws53 --output /tmp/ws53-crypto-profile-new.json
```
