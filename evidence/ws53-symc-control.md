# WS53 SYMC原C控制与格式合同

固定SDK `163d9150ab94a02d09a05f623351f9facee3025e`。脚本从原`hal_symc.c`提取
19个函数和原配置表，加上原表查找函数，共20个未修改函数。原头文件和输入均与
固定提交逐字核对。MMIO、缓存、物理地址转换、时延与CPU身份为主机记录器；没有
运行AES/SM4算法，没有设备访问、密钥装载、Flash或安全配置写入。

通过48项锁/clear/解锁路径、1728项配置编码、16项错误配置、700项描述符、128项
提交、72项IV、16项应答、16项槽选择、10项直接key拒绝及8项指针等待检查。原生
编译启用UBSan trap，重复报告逐字一致。另交叉编译原描述符，确认RV32IMFC/ilp32f
输入32字节、输出16字节，首次/最后/奇偶键位为0/1/9，IV从输入偏移16开始。

关键事实及Rust实现约束：

- SYMC与HASH共享SPACC/IRQ59，但输入、输出描述符和指针独立，不能借用HASH格式。
- 原`set_key`始终返回失败，`attach`仅向九位槽号字段写截断结果。需要独立KM/keyslot
  交接及合成测试密钥流程；不能把随机槽号当作已持有密钥，也不读出生产密钥。
- 实际配置表使用AES=2、SM4=5、128位数据宽度=0；与头文件未使用的同名常量可能
  不同。表可接受不合适的算法/密钥长组合，编码测试不是密码功能合法性测试。
- clear超时的lock错误路径会再clear一次，随后仍解除owner；直接unlock也会在
  clear超时后解除owner。Rust不得据此自动释放内存、密钥槽或共享控制器。
- 请求先读取整字再加通道位；clear ACK写的是请求字，可能带其他通道位。完成ACK
  清选低16位的其余通道，仍保留高16位。主机记录只证明写出的值，不推断硬件W1C。
- 原start先发布输出指针，再执行描述符缓存回调并发布输入指针；可能的提前设备
  读取、缓存一致性与物理排空没有被源码测试证明。Rust必须另建交接合同。
- 原get_iv忽略`iv_len`，总复制16字节。测试使用完整20字节守卫缓冲，没有越界写；
  Rust应使用固定16字节类型。输入的零长度、未对齐地址或32位长度也可被原叶函数
  接受，不能直接继承为安全公开参数。

本轮不覆盖DFA和可选RAW IRQ分支、CCM/GCM的复合处理、驱动层完整参数验证、真实
中断/缓存/时钟或DMA归还。该源码合同是后续RDL/PAC/HAL与模型的输入，不是SYMC
已实现/实板验收声明。源JSON记录每个原函数摘要及控制路径写入顺序。

```sh
uv run --script scripts/check_ws53_symc_control.py \
  --sdk /path/to/fbb_ws53 --output /tmp/ws53-symc-control.json
```

需要原生C编译器及`riscv64-linux-gnu-gcc/objcopy`，可用`--target-cc`与
`--target-objcopy`指定兼容工具。普通Cargo构建不运行此来源审计。
