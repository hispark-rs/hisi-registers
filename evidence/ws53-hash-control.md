# WS53 HASH 通道控制源码审计

固定 SDK `163d9150ab94a02d09a05f623351f9facee3025e`，运行
`scripts/check_ws53_hash_control.py`。脚本逐份比对 SDK 提交与本地输入，
提取未修改的 7 个 C 函数、原始上下文及描述符定义，使用原始寄存器/产品头文件。
主机上的 MMIO、锁竞争、CPU 身份、分配、物理地址与应答副作用均为显式桩。

## 已复现的控制流程

45 个具名场景覆盖通道 1/2、两个 CPU 身份、立即/延迟/永不完成的清除，
五种非空闲所有者、锁写入后回查失败、非法通道、完成应答和退出。
未修改 SDK 的超时常量：永不完成场景执行 10,000,000 次状态读取及延迟调用，
但主机延迟桩不实际睡眠。两次独立编译/执行的 JSON 逐字节一致。

| 路径 | 原函数执行结果 | Rust 适配约束 |
|---|---|---|
| `hal_hash_clear_channel` 超时 | 返回失败，先屏蔽对应完成中断再提交 clear | 有界等待；不能把未完成当成功 |
| `hal_hash_lock` 内部 clear 超时 | 忽略失败，仍启用通道、发布表地址/深度、清空表，最后返回成功 | clear 失败后停止提交；不能继续发布/覆盖 DMA 描述符 |
| `hal_cipher_hash_deinit` | 解锁 0/1，保留通道 2 所有者；随后清零并释放两张表，无 clear/排空检查 | 使用一致的 1/2 通道标识；未证明停止时保留 DMA 内存 |
| `hal_cipher_hash_done_try` | 读取原始状态，仅写回选中通道位；未就绪也会写 0 | 描述为状态与独立应答命令，不生成普通 RMW 接口 |
| 锁占用/回查失败 | 返回忙，不执行后续 clear/发布 | 需要硬件所有权协议；单核临界区不能替代跨核锁 |

这些结果证明源码的访问顺序和错误传播，不证明芯片会发生内存破坏、ACK 确为
W1C、硬件通道数量或中断线路正确。桩中的零值不是复位值。退出后仍保持的通道
所有者也只是原函数作用于明确输入状态的结果，不是当前 A 板状态。

## ABI 与范围

原始描述符 16 字节，每上下文 2 项；长度位于 +4、地址低字位于 +8。
用 `riscv64-linux-gnu-gcc -march=rv32imfc -mabi=ilp32f` 编译原始声明，
提取目标对象的专用常量段，与主机字段探针逐字对照：描述符和控制/密钥控制/
读写指针位布局一致。交叉编译没有执行目标程序，不证明 DMA 可访问性或缓存一致性。

主机启用 UBSan trap 模式。最初动态 UBSan 链接因本机缺少运行库失败，
改用无需外部运行库的 trap 模式后通过；保留初次失败日志，没有宣称它通过。
前一轮应用配置/IRQ 审计的 9 个分发、16 个分配组合重跑，结果完全相同。

当前增量没有新增 RDL/PAC/HAL/QEMU，也没有访问设备、密钥、Flash 或 eFuse。
算法输出、时钟归属、真正的硬件 clear/排空与中断，仍未验收。
